# Connector contract

`detect(url) -> (provider, slug)` is deterministic and rejects unknown hosts. `PublicConnector(provider, slug, company, client)` holds only validated tenant configuration. `fetch(cursor=0)` performs one bounded request and returns JSON. `parse(payload) -> list[JobInput]` validates every record; errors reject the enumeration. `discover() -> Enumeration` traverses every page, rejects repeated identifiers and confirms totals where provided. Normalization is performed during typed JobInput construction; original fields stay in raw.

`complete=True` is required for any reconciliation. Missing arrays, invalid required fields, exceeded response/page limits, repeated pages and total mismatches raise errors. Greenhouse and Ashby expose full arrays; Lever uses skip/limit until a short page (including a final empty page after an exact page multiple). Missing/unlisted Ashby jobs are intentionally excluded when isListed=false. Network failures do not yield empty successful batches.

Required fields: external_id, title, company, description, location, source_url, application_url. Optional fields: employment_type, remote_status, salary object, published_at. Empty descriptions from a successful API remain empty; do not invent content. Greenhouse updated_at is not publication date. Ashby publishedAt is last publication, not guaranteed original creation. Lever source timestamps remain raw unless semantically established.

Provider API references:
- https://docs.greenhouse.io/job-board.html
- https://github.com/lever/postings-api
- https://developers.ashbyhq.com/docs/public-job-posting-api

Adding a provider requires schema fixtures, completeness/pagination tests, failure tests, multiple live tenants, coverage evidence, constraints and documentation. Structured public API first, feed/JSON-LD second, HTML third, browser only with evidence of necessity. Custom-domain detection is backlog.

## Cohort 2

Detection and construction now live in `vindex.connectors.registry`; only implemented providers have factory entries. Provider codes personio-de/personio-com select the documented hosted-domain variant but count as one Personio platform. SmartRecruiters detects careers.smartrecruiters.com and jobs.smartrecruiters.com. Personio detects exactly one validated tenant label under jobs.personio.de/com. Arbitrary custom domains remain unsupported.

SmartRecruiters rejects changed totals/offsets, repeated IDs, non-public listings, mismatched detail IDs and any failed/missing detail. Descriptions combine source job-ad sections as plain text; non-text video sections stay in raw. An explicitly blank jobDescription.text is a source data-quality gap and is retained with quality_flags=["role_description_missing"]. An absent/changed job-description schema still fails the enumeration. No role content is invented to fill an empty source field. Publication retains releasedDate, which is source release time, not necessarily original creation.

Personio reads the full default XML feed using defusedxml with DTD/entities disabled. If descriptions are empty, it tries documented en/de/fr/es/nl/it/pt feed translations; enrichment retains original XML and the chosen translation language. Translation IDs cannot expand the original snapshot. If descriptions remain missing, the run fails. createdAt is retained as source metadata without relabelling it publication date. Salary source text and multiple offices are preserved; no salary currency/unit or remote inference is invented.

All implemented connectors use bounded PublicHTTP reads with provider-controlled hosts, HTTPS, no redirects, 20 MB decompressed response limits and three-attempt retry budgets. Retry-After up to 30 seconds is honored inline; longer waits fail into durable source cooldown.

## Cohort 3: Workday and Recruitee

Workday supports one validated tenant label and wd data-center label under myworkdayjobs.com. Configuration encodes tenant~data-center~career-site within the existing 100-character source key. Optional language prefixes in submitted hosted URLs are recognized; myworkdaysite.com and custom domains are not supported yet. The source externalUrl is preserved for both listing and application entry; no unobserved application route is invented. Source startDate is retained in raw, without asserting original publication semantics.

Only the public, read-only career-search POST is used. Robots rules are loaded before search/detail requests and crawl pacing is enforced. A genuine robots 404 is treated as absent; redirects, authorization errors and other fetch failures abort. First-page total, unique listing paths, stable posting IDs, site/posted state and listing/detail agreement are required. Later pages may report total=0. A terminal empty page or exact first-page reset is accepted at the advertised boundary, followed by first-page/total reconfirmation. Changed or extra terminal paths are rejected. Reported totals at/above 2000 and boards above the 400-detail budget fail closed. This is a bounded implementation; large-board completeness is not claimed. Every failure still preserves indexed jobs.

Recruitee uses its documented /api/feeds/offers.xml endpoint, not the careers JSON API that is moving to mandatory tokens on February 10, 2027. Feed/root/IDs, HTTPS output links and date syntax are checked; DTD/entities and duplicate IDs fail. Descriptions/requirements, publication time, source salary fields, work model and employment type are preserved. Original custom-domain application links are retained even though source registration currently needs the hosted tenant URL.

Primary Recruitee references, checked 2026-11-06:
- https://support.recruitee.com/en/articles/8213076-faq-api
- https://docs.recruitee.com/reference/authentication-1

Workday behavior was observed directly on public employer-hosted boards; no documented integration API guarantee is claimed. Regression evidence includes IMF boundary-offset responses and both IMF/Gates detail samples.

## Cohort 4: hosted Teamtailor, Breezy HR and public Workable

Teamtailor career sites advertise their JSON Feed at `/.well-known/api-catalog`; verified primary examples are https://clearroute.teamtailor.com/.well-known/api-catalog and https://omny.teamtailor.com/.well-known/api-catalog. The adapter reads `/jobs.json` and `/jobs.rss`, validates feed identity and UUID uniqueness, requires both feeds to agree on job identifiers/links, and reconfirms the JSON identifier set. RSS preserves source workplace and multiple locations; JSON preserves descriptions, employment type, salary and publication timestamps. The original job page is the application entry point. Custom domains and paginated feeds (next_url or 100+ items) currently fail closed; do not claim large-board coverage.

Breezy reads the observed public `/json` hosted listing feed, checks it against the public board's job links, and requires successful description/application-link detail extraction for every posting plus a final identifier-set reconfirmation. Maximum 400 details; empty feeds fail until an authoritative empty-board marker is established. Every request follows the career site's robots policy and pacing. These are public website interfaces, not an authenticated employer-management API. The first VALD run failed because a talent-pool detail omitted JobPosting schema; SUBSCRIBE succeeded. The adapter now accepts that source omission only when canonical URL, Open Graph URL, exact title, description element and actual apply link independently establish the detail identity. It retains description HTML and flags `jobposting_schema_missing`; it does not invent Google metadata. The original failed evidence remains committed.

Workable's official [public collection documentation](https://workable.readme.io/reference/jobs-1) and [career-page guide](https://help.workable.com/hc/en-us/articles/115012771647-Using-the-Workable-API-to-create-a-careers-page) describe the complete published jobs collection with `details=true`. The documented www endpoint currently returns a 302 to `https://apply.workable.com/api/v1/widget/accounts/{account}?details=true`. The adapter directly uses that fixed validated API host; it never follows redirects. It preserves all returned locations, original source/application links, descriptions/requirements/benefits, source salary and published_on (not created_at). It requires a named collection, unique shortcodes, expected list schema and a second matching identifier set. No authoritative total is supplied; completeness relies on the documented full-collection contract. Bare `/j/shortcode` URLs cannot identify an employer. Custom domains are not detected yet.

The first LearnWorlds run exposed multiple location rows for the same shortcode, not an invalid identifier format. A posting is now grouped by shortcode only when every non-location field agrees and each variant differs; exact duplicate rows and conflicting titles/descriptions still fail. All raw location variants are preserved and the combined location set is reconfirmed. The failed run remains in evidence rather than being replaced by a different employer.

BambooHR reads the observed public `/careers/list` and `/careers/{numeric-id}/detail` interfaces. The reported integer total must equal all unique listed identifiers and stay within the 400-detail budget. Each detail must match the listed title and URL and report `Open`; every failure aborts the batch. IDs are reconfirmed afterward. Native job pages provide the application entry point. Source description, employment label, datePosted, compensation and location fields remain intact; form-field configuration is not stored. Numeric locationType values have not been semantically verified, so they remain raw with `workplace_type_unmapped`; no remote/hybrid meaning is invented. Empty feeds fail until independent tenant identity can be established. Primary employer career link: https://www.concept2.com/careers. This observed website interface has no claimed vendor API stability guarantee.

Pinpoint uses its documented [public postings feed](https://developers.pinpointhq.com/docs/jobs-json-endpoint), also described in its [external jobs guide](https://help.pinpoint.support/en/articles/5878344-how-to-list-pinpoint-jobs-on-any-website). Do not use deprecated jobs.json: it omits secondary postings. Distinct posting IDs are retained even when their parent job IDs agree. The adapter preserves description sections, locations, workplace/employment labels and source application URLs; custom outgoing links are preserved but not fetched. Compensation is promoted only when compensation_visible=true. Original publication time is not promised by the feed. Duplicate/malformed IDs, unexpected pagination, changing identifier sets and robots denial fail the run. Hosted tenant registration is supported; custom-domain entry detection and translated feed selection remain pending.

## Job-board cohort: Jobboardly and Niceboard investigation

Jobboardly (source brand: Job Boardly) is a distinct required platform. Its hosted sites expose `/jobs` HTML with explicit sequential Next controls, disabled terminal controls, and Showing range counters. The adapter requires all three, validates unique same-host posting paths and every detail's single JobPosting/canonical URL, and preserves actual Apply now destinations without fetching those external destinations. JSON-LD preserves employer, description, salary, employment type, locations and source datePosted; explicit visible workplace badges are retained. A failed detail, invalid range, repeated page/identifier or changed first-page snapshot aborts the run. It is bounded to 400 details/100 pages, rejects empty pages rather than assuming closure, and currently registers only hosted jobboardly.com tenants. Public HTML/JSON-LD behavior was observed on https://recruiter-jobs.jobboardly.com/jobs and https://pennsylvania-communications.jobboardly.com/jobs; no vendor API guarantee is claimed.

Niceboard remains unimplemented. `evidence/cohort5-niceboard-discovery.json` records public root/API probes: AvA and Pro Bono Australia robots policies disallowed `/api/jobs`, so those requests were not made. Jobs in Carbon allowed the request but returned a validation error, not job records. Allowed public HTML is largely a client template; this is not evidence of complete enumeration. Do not bypass robots via browser requests or count these responses as live coverage. A permitted complete feed or a different independently accessible deployment is still needed.
