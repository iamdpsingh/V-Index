# Connector contract

`detect(url) -> (provider, slug)` is deterministic and rejects unknown hosts. `PublicConnector(provider, slug, company, client)` holds only validated tenant configuration. `fetch(cursor=0)` performs one bounded request and returns JSON. `parse(payload) -> list[JobInput]` validates every record; errors reject the enumeration. `discover() -> Enumeration` traverses every page, rejects repeated identifiers and confirms totals where provided. Normalization is performed during typed JobInput construction; original fields stay in raw.

`complete=True` is required for any reconciliation. Missing arrays, invalid required fields, exceeded response/page limits, repeated pages and total mismatches raise errors. Greenhouse and Ashby expose full arrays; Lever uses skip/limit until a short page (including a final empty page after an exact page multiple). Missing/unlisted Ashby jobs are intentionally excluded when isListed=false. Network failures do not yield empty successful batches.

Required fields: external_id, title, company, description, location, source_url, application_url. Optional fields: employment_type, remote_status, salary object, published_at. Empty descriptions from a successful API remain empty; do not invent content. Greenhouse updated_at is not publication date. Ashby publishedAt is last publication, not guaranteed original creation. Lever source timestamps remain raw unless semantically established.

Provider API references:
- https://docs.greenhouse.io/job-board.html
- https://github.com/lever/postings-api
- https://developers.ashbyhq.com/docs/public-job-posting-api

Adding a provider requires schema fixtures, completeness/pagination tests, failure tests, multiple live tenants, coverage evidence, constraints and documentation. Structured public API first, feed/JSON-LD second, HTML third, browser only with evidence of necessity. Custom-domain detection is backlog.

## Cohort 2

Detection and construction now live in `vindex.connectors.registry`; only implemented providers have factory entries. Provider codes personio-de/personio-com select the documented hosted-domain variant but count as one Personio platform. SmartRecruiters detects careers.smartrecruiters.com and jobs.smartrecruiters.com. Personio detects exactly one validated tenant label under jobs.personio.de/com. Arbitrary custom domains remain unsupported.

SmartRecruiters rejects changed totals/offsets, repeated IDs, non-public listings, mismatched detail IDs and any failed/missing detail. Descriptions combine source job-ad sections as plain text; non-text video sections stay in raw. An explicitly blank jobDescription.text is a source data-quality gap and is retained with quality_flags=["role_description_missing"]. An absent/changed job-description schema still fails the enumeration. No role content is invented to fill an empty source field. Publication retains releasedDate, which is source release time, not necessarily original creation.

Personio reads the full default XML feed using defusedxml with DTD/entities disabled. If descriptions are empty, it tries documented en/de/fr/es/nl/it/pt feed translations; enrichment retains original XML and the chosen translation language. Translation IDs cannot expand the original snapshot. If descriptions remain missing, the run fails. createdAt is retained as source metadata without relabelling it publication date. Salary source text and multiple offices are preserved; no salary currency/unit or remote inference is invented.

All implemented connectors use bounded PublicHTTP reads with provider-controlled hosts, HTTPS, no redirects, 20 MB decompressed response limits and three-attempt retry budgets. Retry-After up to 30 seconds is honored inline; longer waits fail into durable source cooldown.

## Cohort 3: Workday and Recruitee

Workday supports one validated tenant label and wd data-center label under myworkdayjobs.com. Configuration encodes tenant~data-center~career-site within the existing 100-character source key. Optional language prefixes in submitted hosted URLs are recognized; myworkdaysite.com and custom domains are not supported yet. The source externalUrl is preserved for both listing and application entry; no unobserved application route is invented. Source startDate is retained in raw, without asserting original publication semantics.

Only the public, read-only career-search POST is used. Robots rules are loaded before search/detail requests and crawl pacing is enforced. A genuine robots 404 is treated as absent; redirects, authorization errors and other fetch failures abort. First-page total, unique listing paths, stable posting IDs, site/posted state and listing/detail agreement are required. Later pages may report total=0. A terminal empty page or exact first-page reset is accepted at the advertised boundary, followed by first-page/total reconfirmation. Changed or extra terminal paths are rejected. Reported totals at/above 2000 and boards above the 400-detail budget fail closed. This is a bounded implementation; large-board completeness is not claimed. Every failure still preserves indexed jobs.

Recruitee uses its documented /api/feeds/offers.xml endpoint, not the careers JSON API that is moving to mandatory tokens on February 10, 2027. Feed/root/IDs, HTTPS output links and date syntax are checked; DTD/entities and duplicate IDs fail. Descriptions/requirements, publication time, source salary fields, work model and employment type are preserved. Original custom-domain application links are retained even though source registration currently needs the hosted tenant URL.

Primary Recruitee references, checked 2026-11-06:
- https://support.recruitee.com/en/articles/8213076-faq-api
- https://docs.recruitee.com/reference/authentication-1

Workday behavior was observed directly on public employer-hosted boards; no documented integration API guarantee is claimed. Regression evidence includes IMF boundary-offset responses and both IMF/Gates detail samples.

## Cohort 4: hosted Teamtailor, Breezy HR and public Workable

Teamtailor career sites advertise their JSON Feed at `/.well-known/api-catalog`; verified primary examples are https://clearroute.teamtailor.com/.well-known/api-catalog and https://omny.teamtailor.com/.well-known/api-catalog. The adapter reads `/jobs.json` and `/jobs.rss`, validates feed identity and UUID uniqueness, requires both feeds to agree on job identifiers/links, and reconfirms the JSON identifier set. RSS preserves source workplace and multiple locations; JSON preserves descriptions, employment type, salary and publication timestamps. The original job page is the application entry point. Custom domains and paginated feeds (next_url or 100+ items) currently fail closed; do not claim large-board coverage.

Breezy reads the observed public `/json` hosted listing feed, checks it against the public board's job links, and requires successful description/application-link detail extraction for every posting plus a final identifier-set reconfirmation. Maximum 400 details; empty feeds fail until an authoritative empty-board marker is established. Every request follows the career site's robots policy and pacing. These are public website interfaces, not an authenticated employer-management API. The first VALD run failed because a talent-pool detail omitted JobPosting schema; SUBSCRIBE succeeded. The adapter now accepts that source omission only when canonical URL, Open Graph URL, exact title, description element and actual apply link independently establish the detail identity. It retains description HTML and flags `jobposting_schema_missing`; it does not invent Google metadata. The original failed evidence remains committed.

Workable's official [public collection documentation](https://workable.readme.io/reference/jobs-1) and [career-page guide](https://help.workable.com/hc/en-us/articles/115012771647-Using-the-Workable-API-to-create-a-careers-page) describe the complete published jobs collection with `details=true`. The documented www endpoint currently returns a 302 to `https://apply.workable.com/api/v1/widget/accounts/{account}?details=true`. The adapter directly uses that fixed validated API host; it never follows redirects. It preserves all returned locations, original source/application links, descriptions/requirements/benefits, source salary and published_on (not created_at). It requires a named collection, unique shortcodes, expected list schema and a second matching identifier set. No authoritative total is supplied; completeness relies on the documented full-collection contract. Bare `/j/shortcode` URLs cannot identify an employer. Custom domains are not detected yet.

The first LearnWorlds run exposed multiple location rows for the same shortcode, not an invalid identifier format. A posting is now grouped by shortcode only when every non-location field agrees and each variant differs; exact duplicate rows and conflicting titles/descriptions still fail. All raw location variants are preserved and the combined location set is reconfirmed. The failed run remains in evidence rather than being replaced by a different employer.

BambooHR reads the observed public `/careers/list` and `/careers/{numeric-id}/detail` interfaces. The reported integer total must equal all unique listed identifiers and stay within the 400-detail budget. Each detail must match the listed title and URL and report `Open`; every failure aborts the batch. IDs are reconfirmed afterward. Native job pages provide the application entry point. Source description, employment label, datePosted, compensation and location fields remain intact; form-field configuration is not stored. Numeric locationType values have not been semantically verified, so they remain raw with `workplace_type_unmapped`; no remote/hybrid meaning is invented. Empty feeds fail until independent tenant identity can be established. Primary employer career link: https://www.concept2.com/careers. This observed website interface has no claimed vendor API stability guarantee.

Pinpoint uses its documented [public postings feed](https://developers.pinpointhq.com/docs/jobs-json-endpoint), also described in its [external jobs guide](https://help.pinpoint.support/en/articles/5878344-how-to-list-pinpoint-jobs-on-any-website). Do not use deprecated jobs.json: it omits secondary postings. Distinct posting IDs are retained even when their parent job IDs agree. The adapter preserves description sections, locations, workplace/employment labels and source application URLs; custom outgoing links are preserved but not fetched. Compensation is promoted only when compensation_visible=true. Original publication time is not promised by the feed. Duplicate/malformed IDs, unexpected pagination, changing identifier sets and robots denial fail the run. Hosted tenant registration is supported; custom-domain entry detection and translated feed selection remain pending.

## Job-board cohort: Jobboardly and Niceboard investigation

Jobboardly (source brand: Job Boardly) is a distinct required platform. Its hosted sites expose `/jobs` HTML with explicit sequential Next controls, disabled terminal controls, and Showing range counters. The adapter requires all three, validates unique same-host posting paths and every detail's single JobPosting/canonical URL, and preserves actual Apply now destinations without fetching those external destinations. JSON-LD preserves employer, description, salary, employment type, locations and source datePosted; explicit visible workplace badges are retained. A failed detail, invalid range, repeated page/identifier or changed first-page snapshot aborts the run. It is bounded to 400 details/100 pages, rejects empty pages rather than assuming closure, and currently registers only hosted jobboardly.com tenants. Public HTML/JSON-LD behavior was observed on https://recruiter-jobs.jobboardly.com/jobs and https://pennsylvania-communications.jobboardly.com/jobs; no vendor API guarantee is claimed.

Niceboard remains unimplemented. `evidence/cohort5-niceboard-discovery.json` records public root/API probes: AvA and Pro Bono Australia robots policies disallowed `/api/jobs`, so those requests were not made. Jobs in Carbon allowed the request but returned a validation error, not job records. Allowed public HTML is largely a client template; this is not evidence of complete enumeration. Do not bypass robots via browser requests or count these responses as live coverage. A permitted complete feed or a different independently accessible deployment is still needed.

The first Jobboardly runs exposed email-only applications and public postings without Google JobPosting metadata. Email destinations stay raw; the normalized application URL points to the original HTTPS posting and carries `application_by_email`. HTML-only postings require matching canonical/Open Graph URL/title, the source's numeric job ID in its Open Graph image path, an employer link, full rich-text description and actual apply destination. Explicit visible employment/workplace/salary/location labels are retained. Relative age labels stay raw without inventing an original posting date. The omission carries `jobposting_schema_missing`; raw.jobposting remains null, and original HTML observations are stored separately rather than fabricating source JSON-LD. Missing/ambiguous identity still fails. Original failure evidence remains committed.

JazzHR hosted applytojob.com sites expose a server-rendered Current Openings list. The adapter requires that template marker, unique validated same-host links/titles and complete HTML documents, then verifies each detail's canonical URL/title, Organization identity, description element and native application form action. It never submits a form or stores candidate form fields/tokens. Description/header HTML remains raw, employment/location labels are preserved and a location explicitly labelled Remote retains that fact. No original publication date or structured salary is invented when this template supplies none; source text remains intact. Maximum 400 details, no custom-domain support, and empty/unexpectedly paginated lists fail closed. A final complete link/title comparison is required. Primary employer examples: https://lapmasterwolters.applytojob.com/apply and https://belaytechnologies.applytojob.com/apply. These are observed public templates, not an authenticated JazzHR account API; demo/sandbox accounts are not coverage examples.

Jobboardly capacity finding: Pennsylvania Communications had at least nine 50-link list pages with further pagination, and the original full detail run timed out at ten minutes. It is not a successful indexing example. The connector now enumerates all list pages within its 400-detail budget before fetching any details, then reconfirms every list page after extraction, including later-page changes. Boards beyond that bound fail early without expensive detail fetches or reconciliations. The known large-board limit is explicit; Jobboardly stays FAILED until its multi-board acceptance is resolved.

## HireHive hosted structured template

The adapter uses public employer HTML, not HireHive's authenticated account API. On https://amcsgroup.hirehive.com/ and https://echelon-dc.hirehive.com/ the root supplies a named ItemList with numberOfItems and contiguous positions. Each listed path is validated under the same hosted tenant, and its JobPosting document must match the listed title, path and canonical URL. The adapter preserves company, description, all structured locations, source datePosted, employment/workplace metadata and baseSalary when provided. A positive integer-valued numeric source identifier is retained as a stable string; fractional/bool identifiers fail. The original attributed JSON-LD URL remains raw while the source's canonical HTTPS posting serves as the native application entry point.

Array and singleton ItemList encodings are supported. Totals must exactly match unique entries and stay within the 400-detail budget before extraction. Reconfirm the whole list after all details. An explicit named zero-total empty list can be a complete observation only after successful reconfirmation; reconciliation still requires two misses separated by 24 hours, and an empty run never counts as live coverage. Missing collections, changed lists, failed details, invalid IDs, robots denial and redirects fail without closures. Custom domains, legacy Embed URL registration and templates without these public structured documents remain unsupported.

Discovery found Zazzle's guessed hosted tenant returned 404; MECIP and NOMM Recruitment lacked the required ItemList. HireHive's own board published a speculative application rather than a specific vacancy, so it was not selected as a coverage example. These findings are separate from the configured independent employer verification and are not successful extraction claims.

## GoHire public hosted boards

GoHire uses three fixed public hosts: jobs.gohire.io for employer identity, visible listings and an explicit job total; api2.gohire.io/widget-jobs/{publicBoardHash} for the full unfiltered collection; and api.gohire.io/widget-job for mandatory detail reads. The case-sensitive public hash comes from the career page's widget script reference and must match the board URL suffix. The widget script itself is not fetched by the connector. This is an observed public website interface, not an authenticated integration API guarantee.

The collection must match the explicit career-page total, all visible first-page links/titles, unique numeric IDs and validated same-board HTTPS posting links. Every detail must match the listing title, employer name, employer ID, employment type and salary. General application pools are excluded. Source text descriptions, location, employment, salary text and original date-only publication are preserved. Form questions, upload settings and unrelated client configuration are not retained. Native posting URLs are application entry points. After extraction both the career-page identity/total/visible links and the complete API collection must match again. Empty boards, unknown schemas/languages, redirects, failures and changed enumerations fail without reconciliation. The bound is 400 details; custom domains and jobs.talentium.io links remain unsupported.

## Polymer documented public API

Primary reference: https://developer.polymer.co/ (Public API, Get All Jobs and Get a Specific Job, checked November 6). Only the unauthenticated organization jobs collection/detail endpoints under fixed api.polymer.co are used. No customer/candidate API or token is used. The named collection must explicitly report page=1, total=1, is_first=true, is_last=true, no next_page, and count equal to its unique item count. Here total is the observed page count; count is the observed job count. Empty and paginated collections currently fail closed, as do more than 400 jobs. This is a bounded adapter, not a claim of large-board support.

All details are mandatory and must match listed numeric IDs, hash, employer, title, employment, location, remoteness, publication time and hosted URL. At least one lifecycle field must be present; any non-null archived_at/closed_at aborts the run. The native job_application_description_url is retained as application entry, source salary text is preserved from the collection, and published_at is distinct from created_at. Form questions/settings are excluded from stored public detail observations. A final complete collection comparison ignores only the clock-dependent relative-age label, which remains preserved in the original listing observation. Robots/pacing and shared HTTP bounds apply. Custom domains and empty-board closure verification remain unsupported.

## Manatal legacy hosted career pages

The adapter registers www.careers-page.com/{tenant} boards and uses the public collection route embedded in their own inline career-page JavaScript: /api/v1.0/c/{tenant}/jobs/, with page_size=50, numeric page and the observed unfiltered publication ordering. It does not use Manatal's authenticated account API. Exact named board identity, embedded clientSlug, an explicit total and visible listing titles bind the API collection to the employer. Public examples: https://www.careers-page.com/quantilehealth and https://www.careers-page.com/munich-ventures-2.

Validate every next/previous link against the fixed host/path and exact query parameters before building the next request from trusted values. Preserve unique numeric IDs and public hashes; require stable totals, terminal count equality, at most 400 jobs/100 pages and successful detail reads for every role. Each HTML detail must match title/Open Graph employer identity, Manatal site identity, heading, board link, full collection description and native application link. Reconfirm both board identity/total/visible links and every API collection page after extraction. Failure, changed/partial lists, malformed IDs, robots denial and empty snapshots never authorize reconciliation.

Original description, locations and visible salary currency/range are retained; salary period is not inferred. Employment type, remote status and original publication time remain null where this template supplies no independent fields; any corresponding source text stays in the description. New tenant subdomain themes/custom domains and empty-board closure verification remain unsupported. No application page/form or candidate data is fetched.

Dover investigation remains unimplemented: older app.dover.com career aliases redirect to jobs.dover.com; direct public-shell assets identify listing routes, but the jobs host's robots policy disallows the collection identity request. The API request was not made. evidence/dover-public-discovery.json records this research blocker; it is not live coverage.

Manatal's first formal run failed because SoupSieve selectors skipped the inert Vue fallback template even though it contained server-rendered jobs. The adapter now parses the specific pre-JavaScript fallback list as its own HTML fragment, preserving the same visible-title/total validation rather than dropping that cross-check. Both failed live runs are retained in evidence/20261106T075732Z-smoke.json.

## Jobboardly documented XML feed expansion

Primary vendor documentation: https://help.jobboardly.com/en/articles/9664028-how-to-use-rss-feeds-and-xml-feeds (checked November 6). Use the full jobs.xml feed, not the latest-only jobs.rss syndication feed. Each XML job retains its stable numeric ID/GUID/canonical path, source employer, full HTML/plain description observations, location, workplace/employment labels, publication/expiry fields, source salary range/currency/schedule and actual application link. Email-only application destinations stay raw with application_by_email and an HTTPS source entry. DTD/entities and duplicate IDs/links/fields are rejected.

The XML record URLs must exactly equal the complete validated HTML roster; every HTML page is enumerated twice and the full XML records are fetched/compared again. This avoids a separate detail request for every listing while retaining an independent full-roster check. The XML path permits at most 5,000 jobs/100 HTML pages, bounded by the existing 20 MB decompressed response cap and ten-minute worker budget. A feed returning documented-disabled 404 falls back to the existing fully checked HTML path with its 400-detail cap. Other errors/robots denial/malformed feeds never become empty snapshots or silent fallback. Earlier oversized-board failures remain valid evidence for the earlier HTML implementation. Feed-enabled large-board live verification is recorded separately.

The first XML smoke completed Recruiter Jobs but Pennsylvania Communications failed because three source application_link fields were bare email addresses rather than URLs. The adapter now validates those explicit addresses syntactically (no delivery/DNS lookup), retains the exact source value, marks application_by_email and uses the original HTTPS posting as the application entry. Malformed destinations still fail. This is the same documented email-entry behavior as mailto links; no destination is guessed or fetched. Initial failure evidence remains committed.

## Recooty current careerspage.io hosted template

Observed public employer boards embed CareersPage/Index state with team identity and the full job_posts array. Bind its unique numeric IDs, actual visible titles/links and visible open-position total before fetching each native detail. Detail state CareersPage/JobDescription must match employer/ID/slug/title, OPEN and APPROVED flags, its source JobPosting ULID/hiringOrganization/canonical URL and a native apply link. Retain original published_at_iso, source employment/workplace/location and provided pay metadata. The original created_at observation is not relabelled publication. Preserve job-bearing list/detail/schema state, excluding unrelated authentication, form, tracking and configuration state.

Reconfirm the complete roster after extraction. The bounded template supports 400 jobs; empty/paginated collections, legacy jobs.recooty.com and www redirects/custom domains are unsupported. Source public examples: https://careerspage.io/augusto-digital and https://careerspage.io/recooty-inc. No browser execution or authenticated API is used; every fixed-host request follows robots/pacing and shared transport bounds.

Recooty live discovery found an explicitly OPEN role in the public careers collection, with matching JobPosting identity and a working native application entry, whose separate job_board_status was NOT_APPLIED. APPROVED-only gating incorrectly rejected this live role. The adapter accepts the two observed flags APPROVED/NOT_APPLIED while still requiring OPEN, complete roster membership and every detail/application identity check; unobserved states remain unsupported, never proof of closure. Original flags remain raw. Initial second-employer failure evidence is preserved.
